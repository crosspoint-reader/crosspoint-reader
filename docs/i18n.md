## For Developers

### Translation System Architecture

The I18N system uses **per-language YAML files** to maintain translations and a Python script to generate C++ code:

```
lib/I18n/
├── translations/                # One YAML file per language
│   ├── english.yaml
│   ├── spanish.yaml
│   ├── french.yaml
│   └── ...
├── I18n.h
├── I18n.cpp
├── I18nKeys.h                   # Enums (auto-generated)
├── I18nStrings.h                # String array declarations (auto-generated)
└── I18nStrings.cpp              # String array definitions (auto-generated)

scripts/
└── gen_i18n.py                  # Code generator script
```

**Key principle:** All translations are managed in the YAML files under `lib/I18n/translations/`. The Python script generates the necessary C++ code automatically.

### Generation runs on every build

`scripts/gen_i18n.py` is a PlatformIO `pre:` script (`extra_scripts` in `platformio.ini`). Every `pio run` calls it with `strip_unused=True`, so the generated files are always current and keys that no source file references are left out. The three generated files (`I18nKeys.h`, `I18nStrings.h`, `I18nStrings.cpp`) are git-ignored; do not commit them.

The script skips the work and prints `Unchanged: all I18n outputs are up to date.` when every output is newer than every YAML file.

You normally never run it yourself. If you want to check a translation file without a full build, run it by hand **with `--strip-unused`**:

```bash
python3 scripts/gen_i18n.py --strip-unused
```

Without that flag the output keeps every unused key and is about 31 KB bigger. The next build then finds the outputs up to date and skips regeneration, so the bloat ships. If you ran it without the flag, run it again with `--strip-unused --force`.

| Option                | Meaning                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `translations_dir`, `output_dir` | Optional positional arguments. Defaults: `lib/I18n/translations` and `lib/I18n/`    |
| `--strip-unused`      | Omit `STR_*` keys that no scanned source file references. The build always does this          |
| `--src-dirs DIR...`   | Directories scanned for `STR_*` uses. Default: `src lib`                                      |
| `--force`, `-f`       | Regenerate even when the outputs are up to date                                               |
| `--verbose`, `-v`     | Print per-key info and warnings and the files written                                         |

### YAML File Format

Each language has its own file in `lib/I18n/translations/` (e.g. `spanish.yaml`).

A file looks like this:

```yaml
_language_name: "Español"
_language_code: "ES"
_order: "1"

STR_CROSSPOINT: "Witch Reader"
STR_BOOTING: "BOOTING"
STR_BROWSE_FILES: "Buscar archivos"
```

**Metadata keys** (prefixed with `_`):
- `_language_name` — Native display name shown to the user (e.g. "Français")
- `_language_code` — C++ enum name (e.g. "FR"). Please use the [ISO Code](https://en.wikipedia.org/wiki/List_of_ISO_639_language_codes) of the language. Must be a valid C++ identifier.
- `_order` — Controls the position in the Language enum (English is always 0)

**Rules:**
- Use UTF-8 encoding
- Every line must follow the format: `KEY: "value"`
- Keys must be valid C++ identifiers (uppercase, starts with STR_)
- Keys must be unique within a file
- String values must be quoted
- Use `\n` for newlines, `\\` for literal backslashes, `\"` for literal quotes inside values

### Adding New Strings

To add a new translatable string:

#### 1. Edit the English YAML file

Add the key to `lib/I18n/translations/english.yaml`:

```yaml
STR_MY_NEW_STRING: "My New String"
```

Then add translations in each language file. If a key is missing from a
language file, the generator will automatically use the English text as a
fallback (and print a warning).

#### 2. Build

The next build runs the generator for you (see [Generation runs on every build](#generation-runs-on-every-build)). It:
- Fills missing translations from English
- Updates the `StrId` enum in `I18nKeys.h`
- Regenerates all language arrays in `I18nStrings.cpp`

#### 3. Use in code

```cpp
#include <I18n.h>

// Using the tr() macro (recommended)
renderer.drawText(font, x, y, tr(STR_MY_NEW_STRING));

// Using I18N.get() directly
const char* text = I18N.get(StrId::STR_MY_NEW_STRING);
```

**That's it!** No manual array synchronization needed.

### Adding a New Language

To add support for a new language (the example uses Greek, which is not shipped):

#### 1. Create a new YAML file

Create `lib/I18n/translations/greek.yaml`. Give it an `_order` no other file uses (the shipped files run from 0 to 26, so the next free one is 27); the generator reports duplicates:

```yaml
_language_name: "Ελληνικά"
_language_code: "EL"
_order: "27"

STR_CROSSPOINT: "Witch Reader"
STR_BOOTING: "ΕΚΚΙΝΗΣΗ"
```

You only need to include the strings you have translations for. Missing
keys will fall back to English automatically.

#### 2. Build

The next build regenerates all the necessary code.

#### 3. Glyphs

The generator refuses a translation that uses a character no UI font can draw, and lists each one
(`CRITICAL: translation(s) use characters no UI font can draw`). A missing glyph draws nothing, so
the alternative is a label with a silent hole in it. Greek would stop here: the UI faces do not carry
the Greek block, so `0x0370,0x03FF` has to go into `UI_LANG_INTERVALS` in
`lib/EpdFont/scripts/convert-builtin-fonts.sh` first, and the faces regenerated. "Can draw" means
every UI face has the character: the three Inter sizes in both weights and Noto Sans 8
(`lib/EpdFont/scripts/ui_font_coverage.py`).

### Chinese, Japanese and Korean

Their characters are not in the Inter faces, and all of CJK is tens of thousands of glyphs. So each of
the three translations gets its own small UI face per size, holding exactly the characters that
translation uses: `lib/EpdFont/builtinFonts/cjk_ui_{zh,ja,ko}_{10,12}.h`, 1-bit like the Inter faces,
cut from the Noto Sans CJK region of the language (the region picks the glyph forms, which differ for
many shared Han characters). `src/CjkUiFonts.cpp` attaches them behind every UI face as fallback
glyphs, all three whatever the UI language, because the language picker draws each language's name
in its own script.

The faces ship compressed, as 2 KB DEFLATE groups (`compress_ui_face.py`, which transforms the
generated header and never re-renders a glyph). UI screens do not prewarm a glyph cache, and a glyph
decoded on its own costs ~2.5 ms on the C3, so a Chinese Settings page decoded that way would add
~180 ms to every draw. The active UI language's two faces are therefore inflated into its language
pack slot, after its strings (see below), and drawn from there like an uncompressed face. Only the
other two languages' glyphs decode per glyph, through `FontDecompressor`: the language picker's names
and CJK book titles.

- **Changing a CJK translation** usually adds characters. Regenerate its faces with
  `python lib/EpdFont/scripts/build_cjk_ui_fonts.py` (it downloads the three Noto Sans CJK OTFs,
  ~16 MB each, on first use); the build fails until you do.
- **Sizes**: `CJK_UI_FONT_SIZES` in `lib/EpdFont/scripts/font-sizes.sh`, 10 and 12 pt. A UI face takes
  the largest CJK size not above its own: 8 and 10 pt UI text draws CJK at 10 pt, 12 and 14 pt at 12 pt.
  A 14 pt CJK size would cost ~125 KB more, for the large UI step alone.
- **Cost**: 97,132 B of flash for the compressed faces of all three languages (175,916 B flat; zh
  599, ja 500, ko 442 glyphs at the time of writing), ~20 KB for their language packs, and ~1.5 KB of
  RAM: the attached copies of the UI faces' tables, the two providers, and the two face tables that
  point into the language pack slot.
- **The font preview sample** (`STR_FONT_PREVIEW_SAMPLE`) stays English in the three files: the font
  selector draws it in the reader font being previewed, not in a UI face, and the built-in reader
  fonts have no CJK. The glyph check cannot see that, because it checks against the UI faces.
- **Line breaks**: wrapped UI text (`GfxRenderer::wrappedText`) also breaks between Chinese and
  Japanese characters, by the reader's CJK line-break rules (kinsoku included). Korean breaks at its
  spaces.
- **Not covered**: anything that is not a UI string. A Chinese book title draws the characters it
  shares with the translations and a box (□) for each of the rest; titles need the reader's CJK font
  as a further fallback (`docs/future_work/cjk.md`). Every CJK face carries that box, and a CJK
  character no face has draws as it rather than as nothing. There is no CJK keyboard, and bold UI
  text draws CJK in the regular weight.

### I18N API Reference

```cpp
// === Convenience Macros (Recommended) ===

// tr(id) - Get translated string without StrId:: prefix
const char* text = tr(STR_SETTINGS_TITLE);
renderer.drawText(font, x, y, tr(STR_BROWSE_FILES));
Serial.printf("Status: %s\n", tr(STR_CONNECTED));

// I18N - Shorthand for I18n::getInstance()
I18N.setLanguage(Language::ES);
Language lang = I18N.getLanguage();

// === Full API ===

// Get the singleton instance
I18n& instance = I18n::getInstance();

// Get translated string (three equivalent ways)
const char* text = tr(STR_SETTINGS_TITLE);              // Macro (recommended)
const char* text = I18N.get(StrId::STR_SETTINGS_TITLE);   // Direct call
const char* text = I18N[StrId::STR_SETTINGS_TITLE];       // Operator overload

// Set language
I18N.setLanguage(Language::ES);

// Get current language
Language lang = I18N.getLanguage();

// Save language setting to file
I18N.saveSettings();

// Load language setting from file
I18N.loadSettings();

// Get character set for font subsetting (static method)
const char* chars = I18n::getCharacterSet(Language::FR);
```

## How the strings reach the screen

For most of this firmware's life every language sat in the app image as
`const` data, and `I18n::get()` returned a pointer straight into it. That cost
**408,668 B** — 366 KB of strings plus a 1,774 B offset table per language —
for 24 languages, of which any one reader uses one. Flash is the binding
constraint on this device, so that had to change.

It now works like this:

| | where it lives | cost |
| --- | --- | --- |
| **English** | app image, uncompressed, with its offset table | 16,347 B |
| **Every other language** | app image, deflate-compressed pack | ~6 KB each |
| **The active language** | decompressed into the tail of the `spiffs` partition, read by `mmap` | 0 B of RAM |

Total in the image: **153,139 B**, down from 408,668 B.

### Why not just decompress into RAM

Because ~30 KB resident, on a device whose steady-state free heap at the Home
screen is under 40 KB, is not affordable. An `mmap`'d flash pointer reads
exactly like the `const` data it replaces, so `I18n::get()` stays two loads and
an add and nothing is retained.

### The pack format

Each pack is a raw deflate stream (no zlib header) over a *self-describing*
blob: one NUL-terminated entry per `StrId`, in order, where an **empty entry
means "this language does not override English for this key"**. That is what
lets the per-language offset table go away entirely — the device rebuilds it by
walking the blob once while it streams it into flash, writing the English
offset for each empty entry. Bit 15 of a table entry still means "use English",
exactly as it did when the tables were shipped.

The window is **4 KB** (`DEFLATE_WINDOW_BITS = 12` in `gen_i18n.py`), and
`FlashLangPartition::INFLATE_RING_BYTES` must match it. A 32 KB window would
save about 7.5 KB of flash across all packs and cost eight times the transient
RAM to unpack one, which is the wrong trade here.

### What happens on the device

`I18n::refreshActiveStrings()` runs when the language is loaded at boot and
whenever it changes. If the flash slot already holds this language *and* this
firmware build — the `stamp` is a CRC32 of the compressed pack, so it catches
both — the slot is simply mapped. Otherwise it is rebuilt: erase, inflate,
derive the table, write, and write the header last so an interrupted build
reads as absent rather than as corrupt.

Rebuilding costs one erase plus ~30 KB of inflate, about a second, and happens
once per language change and once after each firmware update that changes any
string. English readers never pay it. **Any failure falls back to English**
rather than to blank rows.

### What a CJK pack carries besides its strings

An *extension*: bytes written after the strings, built, erased and mapped with
them (`FlashLangPartition::Extension`, registered through
`I18n::setPackExtension()`). Chinese, Japanese and Korean keep their two CJK UI
faces there, inflated from the compressed faces in the image: per size, the flat
bitmap and its offset table, exactly what an uncompressed face carries.

- **The stamp** is the pack's CRC32 mixed with the faces' CRCs, so new font data
  rebuilds the slot as new strings do.
- **The rebuild** adds the faces' inflate, ~0.3 s for Chinese on the C3, and the
  writes. Each face is checked against the CRC32 its header states before the
  slot is trusted.
- **If the extension fails** (it does not fit, a face does not inflate to its
  CRC, a write fails), the strings stand alone and the faces decode per glyph:
  slower, not wrong. The next refresh tries again. If the slot cannot be mapped
  with the faces, the strings are mapped alone.
- **Sizes**: Chinese needs 88,264 B of the slot and Japanese 78,504 B, so they
  map two 64 KB pages; Korean, at 63,508 B, still fits one, as does every other
  language.

### Where the slot lives

The last 128 KB of the `spiffs` partition, which is not a filesystem here — it
is the flash font cache (`FlashFontPartition`) and the TTF glyph store. Both stop
short of the reservation: `beginWrite()` erases and budgets only up to
`fontUsableSize()`, an index reaching past the ceiling is treated as invalid so
the font cache re-derives from the `.cpfont` files on the SD card, and the glyph
store rejects a layout past its region and installs again. The slot was 64 KB
until the CJK UI faces moved into it; the 64 KB more came out of the font cache,
which migrates itself that way on the first boot after the change.

### The verification you get for free

`gen_i18n.py` replays the entire device decode path for every language as it
generates — inflate at the real window size, the same table walk
`TableBuilder::feed()` does, then the same lookup `I18n::get()` does — and
raises if any string does not come back identical. A format mistake fails the
build instead of shipping as a screen full of wrong text.

## File Storage

Language settings are stored in:
```
/.crosspoint/language.bin
```

This file contains:
- Version byte
- Current language selection (1 byte)

The decompressed strings for the active language live in flash, not on the SD
card — see the section above.

## Translation Workflow

### For Developers (Adding Features)

1. Add new strings to `lib/I18n/translations/english.yaml`
2. Build (the generator runs as part of it)
3. Use the new `StrId` in your code
4. Request translations from translators

### For Translators

1. Open the YAML file for your language in `lib/I18n/translations/`
2. Add or update translations using the format `STR_KEY: "translated text"`
3. Keep translations concise (E-ink space constraints)
4. Make sure the file is in UTF-8 encoding
5. Run `python3 scripts/gen_i18n.py --strip-unused --force` to verify the file generates, or just build
6. Test on device or submit for review
