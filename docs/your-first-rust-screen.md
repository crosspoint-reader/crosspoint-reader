# Your first Rust screen with `xpui`

A complete walkthrough: from an empty file to a Rust screen running on a real
device. Every file you need is here in full — copy each block into the path
above it and it will work.

CrossPoint's screens are C++. This tutorial builds one in **Rust**, using the
[`xpui`](../lib/xpui_rs/README.md) framework, running side by side with the C++
ones in the same firmware.

You do not need to know Rust well. You do need the project building already —
see [contributing/getting-started.md](contributing/getting-started.md) if it is
not.

## What you'll build

A screen with a level you can change, and a reading of how long the device has
been awake. Small, but it covers everything: drawing, touch, hardware buttons,
translations, calling _into_ C++ and **teaching C++ something new to say**.

The level belongs to the screen itself. Driving real hardware with it is the
same four edits as step 2, with a setter instead of a getter.

```
┌──────────────────────────────────┐
│  Brightness Demo         100%  ▓ │   <- header, drawn by the theme
├──────────────────────────────────┤
│                                  │
│  Brightness  60%                 │
│                                  │
│   −  ────────●───────────    +   │   <- drag it, or use the side buttons
│                                  │
│  Uptime                  4,321 s │   <- a value that does not exist yet
│                                  │
├──────────────────────────────────┤
│  Back                            │   <- button hints, drawn by the theme
└──────────────────────────────────┘
```

## The shape of it

Nine steps. Three touch C++, five touch Rust, one is just a build.

1. the words the screen shows
2. teach C++ to report uptime — **four files**
3. the screen itself
4. tell Rust the file exists
5. the C++ class that owns the screen
6. a menu entry to open it
7. run it in the simulator
8. a test
9. flash it to a device

## Before you start

One thing catches almost everyone on macOS. If a build fails with
`ModuleNotFoundError: No module named 'littlefs'`, you are running Homebrew's
`pio`, which ships without a module the ESP32 builder needs:

```bash
alias pio="$HOME/.platformio/penv/bin/pio"
```

`./build-and-test.sh` already picks the right one.

## 1. Add the words

Every string the user reads goes through the translation system. Open
`lib/I18n/translations/english.yaml` and add one key at the end:

```yaml
STR_BRIGHTNESS_DEMO: "Brightness Demo"
```

**Do not copy it into the other thirty language files.** A missing key falls
back to English automatically, and that absence is exactly how the project
tracks what still needs translating.

Both languages pick the key up when you build; nothing is generated by hand.

---

## 2. Teach C++ to report uptime

The screen wants to show how long the device has been awake. Nothing exposes
that to Rust yet, so we add it. **Any** new firmware capability follows these
same four edits, and missing one is the most common mistake in this codebase.

### 2a. Write the C++ function

In `src/rust_ffi/device.cpp`, below `cpp_device_battery_percent`:

```cpp
int32_t cpp_device_uptime_seconds() { return static_cast<int32_t>(millis() / 1000); }
```

Everything in `src/rust_ffi/` is a plain C function Rust may call. One file per
concern — device facts here, drawing in `renderer.cpp`, and so on.

### 2b. Declare it to Rust

In `lib/backend_rs/src/raw.rs`, beside the other device entries:

```rust
pub fn cpp_device_uptime_seconds() -> i32;
```

This is Rust promising the linker such a symbol exists. The signature must match
the C++ exactly; nothing checks it for you.

### 2c. Give tests something to link against

`cargo test` runs on your laptop, where there is no firmware — so the symbol
would be missing and the test binary would not link. In
`lib/backend_rs/src/testing.rs`, next to the other device doubles:

```rust
#[unsafe(no_mangle)]
extern "C" fn cpp_device_uptime_seconds() -> i32 {
    UPTIME_SECONDS
}
```

`unsafe(no_mangle)` is not a typo. Exporting a symbol under a fixed name is
unsafe — nothing checks that the C++ side declares it the same way — and Rust
2024 makes you say so.

and a value for it near the top, beside `BATTERY_PERCENT`:

```rust
const UPTIME_SECONDS: i32 = 4_321;
```

**This is the step people forget.** Skip it and everything builds fine until
someone runs the tests, often days later.

### 2d. Wrap it safely

Finally, in `lib/backend_rs/src/device.rs`, add the function screens will
actually call:

```rust
/// Seconds since the device booted.
pub fn uptime_seconds() -> i32 {
    unsafe { raw::cpp_device_uptime_seconds() }
}
```

The `unsafe` stops here. That is this crate's whole job: every call across the C
boundary is wrapped once, so no screen ever writes `unsafe` itself.

## 3. Write the screen

Create `lib/crosspoint_rs/src/activities/settings/brightness_demo.rs`:

```rust
//! A demo screen: move a level, and show how long we have been awake.

use backend::{device, tr};
use xpui::{vstack, List, ListRow, NavigationScreen, Screen, Stepper, Text, View};

pub struct BrightnessDemo {
    level: i32,
}

/// Everything this screen can be told.
#[derive(Clone, Copy)]
pub enum Msg {
    /// An absolute value, from dragging or tapping the track.
    Set(i32),
    /// A nudge of -1 or +1, from the end glyphs or the side buttons.
    Step(i32),
}

impl Default for BrightnessDemo {
    fn default() -> Self {
        Self::new()
    }
}

impl BrightnessDemo {
    pub fn new() -> Self {
        BrightnessDemo { level: 60 }
    }
}

impl Screen for BrightnessDemo {
    type Message = Msg;

    fn body(&self) -> impl View<Msg> {
        NavigationScreen::new(vstack![12;
            Text::new(format!("{}  {}%", tr!(STR_BRIGHTNESS_DEMO), self.level)),
            Stepper::new(self.level)
                .on_change(Msg::Set)
                .on_step(Msg::Step),
            List::new().push(
                ListRow::new("Uptime").value(format!("{} s", device::uptime_seconds())),
            ),
        ])
    }

    fn update(&mut self, message: Msg) {
        self.level = match message {
            Msg::Set(level) => level,
            Msg::Step(delta) => self.level + delta,
        }
        .clamp(0, 100);
    }
}

backend::register_screen!(BrightnessDemo, create_brightness_demo_activity);
```

Four things worth pausing on:

- **`body()` describes, it does not draw.** You return a description; the
  framework measures and paints it. No coordinates anywhere. It runs again on
  every repaint, which is why `uptime_seconds()` is read there and stays current.
- **`update()` is the only place state changes.** Everything arrives as a
  message: one way in, one way out. When it writes to the firmware rather than
  to a local field, guard the write with a changed-check — SPIFFS sectors have a
  finite erase budget, and a stepper sends a message per nudge.
- **`device` comes from `backend`**, never `xpui`. The framework has no idea what
  a CrossPoint is — you gave it the ability to ask in step 2.
- **`register_screen!`** generates the C function the C++ side calls to build
  this screen. Remember the second argument; the next steps use it.

## 4. Tell Rust the file exists

In `lib/crosspoint_rs/src/activities/settings/mod.rs`:

```rust
pub mod brightness_demo;

pub use brightness_demo::BrightnessDemo;
```

The file is named after the type inside it, and the module tree mirrors
`src/activities/` on the C++ side, so the same screen sits in the same place in
both languages.

---

## 5. The C++ class that owns it

The firmware's navigation is C++, so the screen needs a small C++ class. Two
short files, both complete.

`src/activities/settings/BrightnessDemoActivityRs.h`:

```cpp
#pragma once

#include "activities/ActivityRs.h"

// The factory function register_screen! generated in step 3.
extern "C" {
void* create_brightness_demo_activity();
}

class BrightnessDemoActivityRs final : public ActivityRs {
 public:
  explicit BrightnessDemoActivityRs(GfxRenderer& renderer, MappedInputManager& mappedInput);

  const char* getTitle() const override;
};
```

`src/activities/settings/BrightnessDemoActivityRs.cpp`:

```cpp
#include "BrightnessDemoActivityRs.h"

#include <I18n.h>

#include "I18nKeys.h"

BrightnessDemoActivityRs::BrightnessDemoActivityRs(GfxRenderer& renderer,
                                                   MappedInputManager& mappedInput)
    : ActivityRs("BrightnessDemoRs", renderer, mappedInput, create_brightness_demo_activity) {}

const char* BrightnessDemoActivityRs::getTitle() const { return tr(STR_BRIGHTNESS_DEMO); }
```

`ActivityRs` does everything else: it builds the Rust screen through that
factory, drives its lifecycle, and hands it the renderer and input.

The title stays on the C++ side deliberately — it is read fresh on every render,
so changing language updates the header immediately.

## 6. Open it from the menu

Three edits in `src/activities/settings/SettingsActivity.*`.

In the header, add an entry to `enum class SettingAction`:

```cpp
  BrightnessDemo,
```

In the `.cpp`, add the include at the top:

```cpp
#include "BrightnessDemoActivityRs.h"
```

a row, beside the other `systemSettings.push_back` lines in
`rebuildSettingsLists()`:

```cpp
systemSettings.push_back(
    SettingInfo::Action(StrId::STR_BRIGHTNESS_DEMO, SettingAction::BrightnessDemo));
```

and the case that opens it, in `toggleCurrentSetting()`:

```cpp
case SettingAction::BrightnessDemo:
  startActivityForResult(std::make_unique<BrightnessDemoActivityRs>(renderer, mappedInput),
                         resultHandler);
  break;
```

## 7. Run it

```bash
./build-and-test.sh      # formatting, lints and tests — seconds, no build
./build-and-test.sh sim  # then build the simulator and launch it
```

Navigate to **Settings → System → Brightness Demo**. The simulator needs a
one-time setup; see [simulator.md](simulator.md).

Try all of it: drag the track, tap `−` and `+`, use the side buttons. Every one
works because `Stepper` declared what it responds to — you wrote no input
handling at all. The uptime row climbs as the screen repaints.

If the build fails, read the **first** error rather than the last; Rust errors
cascade.

## 8. Write a test

`update()` is an ordinary function, so the screen is testable with no hardware.
Add this at the bottom of `brightness_demo.rs`, the file you wrote in step 3:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn level_clamps_to_range() {
        let mut screen = BrightnessDemo::new();

        screen.update(Msg::Set(40));
        screen.update(Msg::Step(5));
        assert_eq!(screen.level, 45);

        screen.update(Msg::Set(200));
        assert_eq!(screen.level, 100, "values clamp");
    }

    #[test]
    fn uptime_reaches_the_screen() {
        // Proves step 2 is wired through: declaration, double and wrapper.
        assert_eq!(device::uptime_seconds(), 4_321);
    }
}
```

It lives beside the code rather than in `tests/` because `level` is private, and
a file in `tests/` is a separate crate that cannot see it. The doubles from step
2c are what let this link without a device attached.

```bash
./build-and-test.sh check
```

**Then break it on purpose.** Remove the `.clamp(0, 100)` and confirm the first
test fails. A test you have never seen fail is not yet evidence of anything —
that habit has caught real mistakes in this codebase more than once.

## 9. Put it on the device

Plug the reader in over USB-C. First find out which chip it is; the firmware
differs, and the wrong one simply will not boot:

```bash
~/.platformio/penv/bin/python ~/.platformio/packages/tool-esptoolpy/esptool.py \
  --port /dev/cu.usbmodem2101 chip_id
```

Read the `Chip type` line and match it:

| Chip     | Environment                        |
| -------- | ---------------------------------- |
| ESP32-C3 | `default`                          |
| ESP32-S3 | `sticky` |

Then build, flash and watch it boot:

```bash
~/.platformio/penv/bin/pio run -t upload
~/.platformio/penv/bin/pio device monitor
```

**You cannot brick it this way.** The first-stage bootloader lives in mask ROM
and cannot be overwritten, so the worst case is a device that does not boot —
hold **BOOT**, tap **RESET**, flash again. For a restore point first:
`esptool read_flash 0x0 0x1000000 backup.bin`.
